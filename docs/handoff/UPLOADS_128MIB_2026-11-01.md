- Maximum document file size: **134,217,728 bytes (128 MiB)**.
- PHP-FPM configuration: `upload_max_filesize=128M`, `post_max_size=140M`, `memory_limit=512M`. These were verified in the actual FPM process, including its effective application maximum, rather than inferred from CLI settings.
- Multipart upload endpoints and owner/purpose-bound references remain compatible with the existing UI. PDF, IMRAD, and resource uploads use bounded encrypted storage.
- `ACADEX_MAX_UPLOAD_BYTES=0` selects the automatic 128 MiB limit. A positive value can only lower it. PHP ceilings and a minimum fixed memory envelope still apply.
- The existing global upload slot, shared per-owner rate limit, 20 pending-reference limit, 256 MiB encrypted pending-byte budget, and 2 GiB free-space reserve remain effective. Two full-size pending files may exceed the encrypted-byte quota due to framing overhead; submitting/claiming an upload releases it from the pending budget.
- PHP-rejected oversized files return 413 without trying to read a missing temporary file. Partial/failed transfers return a controlled 422. Request bodies above PHP's post limit retain the existing JSON 413 handler.
- Upload first persists/stages the complete encrypted document. Automatic extraction is optional: files above **20 MiB** bypass synchronous PDF parsing/OCR and return empty editable metadata. The same size guard applies at final submission and in indexing/maintenance consumers, so large accepted files do not subsequently reach whole-PDF parsers.
- Additive upload response field `data.extraction_status`: `complete`, `skipped`, `manual_required`, or `unavailable`. Existing `pdf_path`, `pdf_original_name`, and `extracted` fields remain. An extractor exception does not discard a securely staged upload.
- `MAX_AUTOMATIC_EXTRACTION_BYTES` may lower the automatic-processing ceiling, never raise it above 20 MiB. This is intentionally independent of the accepted file size. OCR's existing page/pixel limits remain.
- No background worker, paid OCR API, resumable upload endpoint, or browser UI was added. Large files are stored intact and can be submitted with manually entered metadata. Full-text indexing is not promised for large documents.

## Storage format and retrieval

New files use PHP's Sodium secretstream XChaCha20-Poly1305 implementation with 1 MiB plaintext chunks. The key is derived from the existing Laravel application key using HKDF-SHA256 with a distinct document-format context. A version marker and stream header precede length-bounded authenticated messages; an empty authenticated FINAL message and EOF are mandatory. Corruption, reordering, omitted frames, truncation, appended data, incorrect keys, and excess plaintext length fail closed. Existing explicitly configured previous application keys are supported.

Encryption writes only ciphertext to an exclusive private local file (`x+b`, mode 0600); failure closes handles and removes only that operation's incomplete file. The local filesystem requirement is explicit. Existing Laravel encrypted strings remain readable using the original application key, without a storage/data migration. Explicit legacy-plaintext conversion remains opt-in and skips the new format.

Every PDF/IMRAD/resource response, including visitor routes, now authenticates the entire document before constructing a successful response. It then decrypts from the same locked ciphertext handle to the response in bounded chunks, releasing the handle on completion. Large plaintext is not spooled to disk. Authorization, resource-parent checks, visitor publication tiers, download restrictions, audit behavior, and private/no-store headers remain in force. Small extraction jobs may use the existing restricted private temporary directory and clean it in `finally`.

### Rollback rule

**After any new-format upload is accepted, do not switch back to the old `6740efc` reader.** It cannot read these new files. Preserve this release's reader, streaming responses, and extraction guards in any forward fix or compatible rollback. To stop accepting large files, lower `ACADEX_MAX_UPLOAD_BYTES` while retaining this implementation. Never restore an older database/storage snapshot over documents accepted since that snapshot. Keep the original `APP_KEY` and the environment/database/encrypted-storage recovery set together.
